# 정산 완료 자동화 성능 검증

## 목적

정산 건수가 늘어날 때 수동 완료 부담을 줄이기 위해 자동 완료 작업을 만들고, 1,000/10,000건에서 개선 전후 처리 비용을 비교했다. 실제 송금과 정산 생성은 테스트 범위에 포함하지 않는다.

대기 상태(`PENDING`)이고 완료 가능 시각(`eligibleAt`)이 작업 기준 시각(`cutoff`) 이하인 ID를 조회한다. 100건씩 조건부 벌크 UPDATE하고 청크별로 커밋한다. DB 오류가 발생하면 실패 청크는 롤백하고 중단하며, 앞선 커밋은 유지한다. 원인 제거 후 같은 cutoff와 판매자 범위로 남은 대상을 다시 처리한다.

## 환경

- 전용 PostgreSQL `settlement_perf`, perf 주문 서버, JMeter
- 실행 구성: `docker-compose.perf.yml`, 외부 네트워크 `parut-net`
- 요청 대상: `POST http://localhost:18083/api/v1/perf/settlements/complete`
- 권한: ADMIN, 입력: cutoff와 실험 sellerId
- 청크 크기: 일반/perf 모두 100건 (`settlement.completion.chunk-size`)
- perf에서는 정기 실행하지 않는다. 일반 환경은 `settlement.completion.cron` 설정 시 실행하며 시간대는 `Asia/Seoul`이다. 처리자는 주문 서비스의 공통 `app.system-account-id`를 사용한다. 일반 환경의 기본값은 임시 UUID이므로 운영 전 SYSTEM 계정 값으로 지정한다.

### 모니터링

공통 Prometheus에 `order-perf:8080/actuator/prometheus`가 수집 대상으로 등록되어 있다. 공통 모니터링과 전용 테스트 서버를 실행하면 기존 APM에서 지표를 확인할 수 있다.

- Prometheus: `up{job="order-perf"}`가 1이면 정상 수집이다. 0이면 서버/네트워크를, 결과가 없으면 활성 수집 설정을 확인한다.
- 기존 APM: application=`order`, instance=`order-perf:8080`, HikariPool-1 선택

기존 Prometheus가 설정 추가 전부터 실행 중이었다면 `docker restart prometheus`로 설정을 반영한다. 테스트 서버가 꺼져 있으면 대상은 DOWN으로 표시되지만, 공통 수집 실패/CPU 알림은 `-service`로 끝나는 job만 감시하므로 `order-perf`는 제외된다.

## 테스트 조건

| 항목 | 조건 |
| --- | --- |
| 목적 | 처리 건수별 배치 성능 비교 |
| 대상 | 1,000건 / 10,000건, 각각 3회 |
| 실행 | 단일 작업자, 요청 1회가 완료 작업 전체 실행 |
| 준비 | 측정 전 별도 100건 워밍업 1회, 회차별 실험 데이터 초기화 |
| 비교 | Job 전체 시간, 내부 조회/UPDATE/트랜잭션 비용, 최종 DB 상태 |

1,000/10,000건은 비교용 작업량이며 운영 정상량이나 한계값은 아니다. [Microsoft 공식 한국어 문서](https://learn.microsoft.com/ko-kr/azure/well-architected/performance-efficiency/performance-test)의 목적별 구분을 참고해, 이번 검증은 같은 작업량의 개선 비교로 정리한다. 추가 Stress Test는 작업량/자원을 바꾸며 한계 부하의 동작을 확인하는 별도 실험이다. 이번에는 개선 효과를 비교하므로 추가하지 않으며 최대 처리 용량을 주장하지 않는다. 용량이나 처리 기한 검증이 필요하면 중단 기준과 함께 재설계한다.

## 데이터 준비와 실행

아래 명령은 저장소 루트에서 전용 DB와 perf 서버가 실행된 상태로 사용한다. SQL은 이번 완료 실험 정산을 초기화하므로 작업 실행 중에는 적용하지 않는다. 기존 생성 검증 데이터와 입력 주문 픽스처는 보존한다.

```bash
docker compose --env-file /dev/null -f docker-compose.perf.yml exec -T postgres-perf \
  psql -X -v ON_ERROR_STOP=1 -U settlement_perf -d settlement_perf -v count=1000 \
  < order-service/performance-test/settlement/data/settlement-completion-job-seed.sql

# 시딩 완료 후 현재 UTC 시각을 대상 기준으로 고정한다.
cutoff=$(date -u +%Y-%m-%dT%H:%M:%SZ)
run_dir="order-service/test-results/settlement-completion/manual-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$run_dir"

# 별도 판매자의 100건 워밍업 작업. 본 측정 통계에서 제외한다.
jmeter -n -t order-service/performance-test/settlement/jmeter/settlement-completion-job-test.jmx \
  -Jcutoff="$cutoff" -JsellerId=f9000000-0000-4000-8000-000000000003 \
  -JexpectedCount=100 -l "$run_dir/warmup.jtl" -j "$run_dir/warmup.log"

jmeter -n -t order-service/performance-test/settlement/jmeter/settlement-completion-job-test.jmx \
  -Jcutoff="$cutoff" -JsellerId=f9000000-0000-4000-8000-000000000002 \
  -JexpectedCount=1000 -l "$run_dir/result.jtl" -j "$run_dir/jmeter.log"
```

10,000건 실행 시 SQL의 `count`와 JMeter의 `expectedCount`를 모두 10000으로 맞춘다. JMX는 한 요청으로 작업 전체를 실행한다. 기본 호스트/포트는 `localhost:18083`이며 필요하면 `-JorderHost`, `-JorderPort`로 변경한다.

반복 비교는 회차마다 실험 정산을 초기화하고 별도 결과 경로를 사용한다. 아래 기록의 워밍업은 전체 측정 전 별도 100건 작업 1회이며, 매 회차 워밍업과 구분한다. 시드를 다시 적용하면 워밍업 행도 PENDING으로 돌아오지만 측정 sellerId와 분리되어 있다.

### 확인 기준

- 응답 `succeeded`가 기대 건수이고 `skipped=0`인지 확인한다.
- JTL 오류 여부와 작업 로그의 `CompletionRun`을 함께 확인한다. HTTP 시간과 `totalMs`는 다르다.
- DB에서 측정 sellerId와 `created_by='settlement-completion-perf'`로 한정하여 완료 건수, 금액, 버전, 처리자와 감사 필드를 대조한다.
- 같은 cutoff와 판매자 범위로 재실행하면 기존 완료 건은 다시 갱신되지 않아야 한다. 이때 기대 건수는 0으로 바꾼다.
- 반복 측정 전 DB 대조를 마친 뒤 다음 시드를 적용한다.

## 관측 지표

`settlement.completion.phase` 타이머와 응답/로그의 시간을 사용한다. 실행 ID는 로그와 응답에만 남기고 메트릭 태그로 쓰지 않는다.

| 구간 | 의미 |
| --- | --- |
| total / totalMs | 작업 전체 시간, HTTP 왕복과 별도 |
| selection / selectionMs | 후보 조회 Repository 호출 누적시간 |
| mutation / mutationMs | 조건부 UPDATE 호출 누적시간 |
| chunk_transaction / chunkTransactionMs | Processor 프록시 호출부터 커밋 후 반환까지의 누적시간 |
| transactionBoundaryMs | 청크 트랜잭션 시간에서 mutation을 뺀 잔여시간 |

잔여시간은 순수 커밋/fsync 시간이 아니다. 하위 타이머가 상위에 포함되므로 합산하지 않는다. 과거 건별 처리 결과의 `lookup`, `item_transaction`은 현재 구간 이름과 구분한다.

기존 SpringBoot APM의 CPU Usage, Heap Used, Connections 패널을 사용한다. Connections에는 Active, Idle, Pending이 함께 표시된다. 내부 처리시간과 호출 횟수는 응답/로그의 원시 결과로 비교한다. 자원 그래프는 여러 회차와 준비 활동이 섞인 관측값이며 짧은 작업의 순간 최대값을 보장하지 않는다.

## 실제 측정 시간대의 화면

2차 Before와 100건 청크 After의 원시 결과 시작/종료 시각을 포함하도록 양쪽 모두 35초 구간을 선택했다. 각 구간은 1,000/10,000건 각 3회와 준비 활동이 함께 있는 시간대다.

PR에는 각 구간의 CPU/Heap과 커넥션 화면을 첨부한다. 처리시간 감소율은 위 원시 응답의 건수별 중앙값으로 판단하고, Grafana는 같은 시간대의 자원 관측을 보조한다. Pending 관측값 0이나 낮은 CPU만으로 대기 부재 또는 병목 원인 제거를 확정하지 않는다. After의 Active가 0으로 표시되더라도 실제 DB 작업이 없었다는 뜻이 아니라 수집 시점에서 포착되지 않을 수 있다는 뜻이다.

캡처는 기존 APM의 쿼리를 유지하고 패널 배치, 범례와 표시 축만 임시 조정했다. CPU는 양쪽 0~10%, Connections는 양쪽 0~10으로 맞췄으며 공통 대시보드에 저장하지 않았다. Heap Used는 구간의 마지막 수집값으로 평균이나 최대값이 아니다. CPU의 System은 실행 환경 전체, Process는 선택한 JVM의 사용률이다.

재현용 시간 범위(KST): Before `2026-10-19 02:04:48~02:05:23`, After `2026-10-19 02:12:20~02:12:55`. 이는 각 작업의 실행시간이 아니라 원시 결과의 실행 시각을 포함한 관측 구간이다.

## 성능 비교

### 1차: 건별 SELECT 제거

대상 ID 조회 후 반복하던 건별 findById와 엔티티 변경을 건별 조건부 UPDATE로 바꾸고 독립 커밋을 유지한 비교다. 현재 청크 구현의 결과와 구분한다.

| 건수 | 최초 Before 중앙값 ms | 1차 After 중앙값 ms | 관측 감소 |
| ---: | ---: | ---: | ---: |
| 1,000 | 298.12 | 210.30 | 29.5% |
| 10,000 | 2,129.64 | 1,703.34 | 20.0% |

Repository findById 호출은 N회에서 0회, UPDATE는 N회로 확인했다. 10,000건의 기존 조회 누적 중앙값은 467.94ms였다. mutation의 측정 경계가 달라 해당 구간만의 개선율은 계산하지 않는다.

### 2차: 100건 청크 벌크 UPDATE

1차 After 값을 재사용하지 않고 현재 건별 조건부 UPDATE 코드를 다시 측정한 2차 Before와 비교했다.

| 건수 | 2차 Before 중앙값 ms | 청크 After 중앙값 ms | 관측 감소 |
| ---: | ---: | ---: | ---: |
| 1,000 | 210.37 | 62.01 | 70.5% |
| 10,000 | 1,893.79 | 241.52 | 87.2% |

| 내부 누적시간 중앙값 | 1,000건 Before → After ms | 10,000건 Before → After ms |
| --- | ---: | ---: |
| 후보 조회 | 24.93 → 33.50 | 49.06 → 58.18 |
| 트랜잭션 포함 | 186.31 → 26.29 | 1,841.82 → 182.23 |
| UPDATE 호출 | 86.17 → 18.52 | 732.49 → 125.26 |

후보 조회는 11/101회로 유지했고 UPDATE Repository 호출은 1,000/10,000회에서 10/100회로 줄었다. After는 프록시 정상 반환 뒤 `committedChunks` 10/100을 기록했다. DB 전체 SQL 문장/커밋 통계를 직접 측정한 값과는 구분한다. 트랜잭션 단위가 달라 누적시간으로 비교하며, 구간별 중앙값의 합이 전체 중앙값과 같다고 가정하지 않는다.

### 비교 조건과 한계

- 전용 DB, 단일 작업자, ID 조회 100건, 1,000 → 10,000건을 3묶음 실행했다.
- 측정 전 별도 100건 작업 1회, 회차별 새 JMeter 프로세스와 실험 정산 초기화를 적용했다. ANALYZE와 진단 EXPLAIN은 측정 밖에서 수행했다.
- After 배포로 서버가 재시작됐고 측정 전에 소량/경합 검증을 수행했다. JIT, 캐시, DB 물리 상태와 고정 순서 효과를 완전히 통제하지 못했다.
- 공통 완료 시각, 트랜잭션 경계와 계측 횟수 변경을 포함한 로컬 각 3회 비교다. SQL 호출 감소만의 순수 인과 효과나 운영 성능 보장값은 아니다.
- 운영 SLO, 최대 수용량, 다중 판매자 분포와 실제 지급 안정성은 검증하지 않았다.

## 정합성, 경합과 복구 결과

아래는 기존 100건 청크 구현의 검증 기록이다. 이후 설정의 검증은 추가 비교 결과를 참고한다. 기존 정산 회귀 테스트 19개가 통과했다.

- 정상 10건의 금액, 버전, 처리자, 감사 정보와 청크 공통 완료 시각을 확인했다. 같은 cutoff 재실행은 0건이며 이미 완료 1건/미래 대상 2건을 제외한 7건 완료도 확인했다.
- 250건 중 두 번째 청크의 특정 행 변경을 임시 CHECK 제약으로 막았다. 첫 100건은 커밋, 두 번째 100건은 전체 PENDING으로 롤백, 작업은 HTTP 409로 중단됐다. 제약 제거 후 같은 cutoff로 150건을 복구했고 앞선 100건은 유지됐다.
- 별도 DB 세션의 행 잠금과 UPDATE 대기 2개를 확인한 뒤 해제했다. 자동 우선은 자동 10건/수동 FAILED, 수동 우선은 수동 1건/자동 9건과 제외 1건, 두 서버 자동 경합은 성공 10건/제외 10건이었다. 해당 행의 version 1과 처리자/감사자를 확인했다.
- 같은 JVM 중복 작업은 HTTP 409로 차단됐다. 임시 제약과 서버를 제거하고 idle-in-transaction 0을 확인했다.
- After 총 33,000건에서 불일치/중복 0, 청크 공통 완료 시각과 기존 37,491건 전체 행 지문 보존을 확인했다.

1차 단계의 기존 테스트 165개 결과와 이번 정산 테스트 19개 결과는 실행 범위가 다르다. 이번 청크 변경에서 전체 165개를 다시 통과한 것으로 해석하지 않는다.

## 트레이드오프와 미구현 범위

- 청크는 UPDATE 호출과 커밋 횟수를 줄이지만 DB 오류 시 설정한 청크 크기까지 함께 롤백한다. 건별 부분 성공과 동일한 실패 단위가 아니다.
- 벌크 UPDATE는 엔티티 메서드와 JPA 감사 콜백을 우회한다. 상태/시간 조건, version 증가와 감사 필드를 명시했으므로 정책 변경 시 수동 경로와 함께 검토해야 한다.
- 0건 갱신 원인을 개별 조회로 구분하지 않고 제외로 집계한다. 상세 원인 분석에는 추가 조회나 이력이 필요하다.
- cutoff는 시각 자격만 고정한다. 과거 eligibleAt을 가진 지연 삽입까지 대상 목록을 고정하지 않는다.
- 재실행은 남은 PENDING을 다시 선정한다. 최초 명단이나 청크 경계를 복원하지 않으며 재실행 청크의 완료 시각은 새로 기록한다.
- 커밋 응답이 끊기면 실패로 단정하지 않고 DB 상태를 확인해야 한다. AtomicBoolean은 같은 JVM만 보호하며 분산 작업 전체의 단일 실행을 보장하지 않는다.
- 대상 스냅샷, 영속 실행 이력과 체크포인트는 미구현이다. 후속 검증 대상은 과거 eligibleAt 지연 삽입, 서버 중단/재시작, 정산 변경과 체크포인트의 원자성이다.
- 운영 수동 복구 진입점과 전체 주문 통합 검증은 별도 범위다.

### 3차: 조합 비교 기록, 이후 분리 비교로 선택 변경

완료 이력 다수/PENDING 소수의 임시 분포에서 ID 순서의 부분 인덱스가 후보 탐색을 줄였다. 전체 상태/ID 인덱스보다 저장 범위가 작으며 이번 임시 갱신 실험에서 뚜렷한 추가 비용은 관측하지 못했다. 원본 마이그레이션은 기존 목록 인덱스를 유지한다. 현재 정산 상태/조회 파라미터에 따라 부분 인덱스가 선택되지 않을 수 있으므로 모든 조회가 빨라진다고 보장하지 않는다.

부분 인덱스를 유지한 100/250/500건 탐색의 10,000건 중앙값은 240.86/227.76/163.39ms였다. 설정별 각3회, 고정 순서와 서버 재생성 조건으로 최적 크기를 확정한 실험은 아니다. 당시 비교 설정은 perf 500건이었다.

빌드 작업과 겹친 최초 기준선은 최종 비교에서 제외하고, 같은 JAR에서 후보 인덱스 없음/100건과 부분 인덱스/500건을 다시 비교했다. 기준 측정 동안 새 인덱스만 일시 제거했고 측정 후 복구했다.

| 건수 | 기준 중앙값 ms | After 중앙값 ms | 관측 감소 | 조회 횟수 | 커밋 보고값 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 61.64 | 43.78 | 29.0% | 11 → 3 | 10 → 2 |
| 10,000 | 257.96 | 157.42 | 39.0% | 101 → 21 | 100 → 20 |

전용 DB, 1,000/10,000건 각3회, 회차별 완료 실험 데이터 초기화, 별도100건 워밍업1회와 기존 JMeter 계획을 사용했다. 대표값은 Job totalMs이며 HTTP시간과 다르다. 소스/설정 지문과 한계는 결과의 comparison.json에 기록했다. 인덱스와 청크를 함께 변경한 결과이므로 다음 단계에서 효과를 분리했다.

당시 500건 설정의 보완 검증은 다음과 같다.

- 기존 정산 회귀 테스트 19개 통과.
- 이미 완료1건/미래2건은 전체 행 불변, 정상7건 완료와 재실행0건 확인.

### 4차: A/B/C/D 효과 분리와 청크 범위 비교

같은 JAR에서 A(기존 인덱스/100), B(부분 인덱스/100), C(기존 인덱스/500), D(부분 인덱스/500)를 비교했다. 순서는 A→B→D→C / B→C→A→D / C→D→B→A / D→A→C→B의 네 묶음이며 실제 배열은 conditions.json을 기준으로 한다. 각 구성은 네 위치에 한 번씩 오고, 짝수 묶음은 10,000→1,000건으로 측정 순서를 바꿨다. 구성마다 서버 재생성 후 별도100건 워밍업, 회차별 시드 초기화와 ANALYZE, 같은 JMeter 계획을 사용했다.

| 구성 | 1,000건 중앙값 ms | 10,000건 중앙값 ms |
| --- | ---: | ---: |
| A 기존 인덱스/100 | 66.43 | 263.38 |
| B 부분 인덱스/100 | 76.42 | 265.97 |
| C 기존 인덱스/500 | 37.20 | 177.59 |
| D 부분 인덱스/500 | 43.19 | 176.89 |

인덱스 효과는 A/B와 C/D를, 청크 효과는 A/C와 B/D를 비교했다. 10,000건의 묶음별 감소율 중앙값은 인덱스100건 조건 -1.23%, 인덱스500건 조건 +1.44%였다. 인덱스500건 조건은 -11.40%~+16.90%로 방향과 크기가 흔들렸다. 통계적으로 효과가 없음을 입증한 것이 아니라 이번 조건에서 채택 근거가 일관되지 않았다는 판단이다.

청크100→500은 10,000건에서 인덱스 유무 각각4묶음 모두 빨랐다. 묶음별 감소율 중앙값은 기존 인덱스31.46%, 추가 인덱스33.79%였다. 구성별 중앙값의 감소율과 묶음별 감소율 중앙값은 다른 통계다. 이전 조합 비교의39.0%를 인덱스만의 효과로 쓰지 않는다.

추가로 인덱스 없는250/500건을 순서250→500, 500→250, 250→500, 500→250의 네 묶음으로 비교했다.

| 청크 | 1,000건 중앙값 ms | 10,000건 중앙값 ms | 최대 실패 청크 범위 |
| ---: | ---: | ---: | ---: |
| 250 | 38.65 | 212.14 | 250건 |
| 500 | 58.26 | 191.52 | 500건 |

1,000건은250건이4회 모두 빨랐다. 10,000건은500건이3회 빠르고1회 거의 같았으며250건의 한 회차366.11ms 편차도 있었다. 구성별4회로 원인이나 운영 분포를 확정하지 않는다. 서로 다른 단계인 A의100건과 이250건을 직접 비교해 단독 개선율을 계산하지 않는다.

인덱스 단독 이득이 일관되지 않아 추가 인덱스는 취소했다. 당시 perf에는 250건을 선택했으며, 다음 단계에서 네 청크 크기를 같은 조건으로 비교했다. 특정 판매자와 고정 금액 픽스처를 사용한 결과이며, 모든 크기의 경합 대기를 동시에 비교한 실험은 아니다.

측정에서 처리한 정산 264,000건의 DB 불일치/중복 0, 기존 생성37,491건 보존을 확인했다. 당시 250건 설정의 정상/재실행/롤백 복구와 기존 정산 테스트 결과는 해당 검증 원본으로 구분한다.

## 수동과 자동 완료를 구분한 이유

| 항목 | 수동 관리자 완료 | 자동 완료 작업 |
| --- | --- | --- |
| 대상 | 관리자가 선택한 최대 50개 ID | cutoff까지 자격이 있는 PENDING을 커서 조회 |
| 업무 조건 | PENDING, eligibleAt <= 요청 처리 기준 시각 | PENDING, eligibleAt <= 작업 시작 시 고정한 cutoff |
| 저장 | 엔티티 변경 감지와 @Version | 조건부 벌크 UPDATE, version과 감사 필드 명시 |
| 완료 시각 | 요청 내 공통 시각 | 청크별 공통 시각 |
| 실패 경계 | 예상한 업무 오류/충돌은 건별 실패, 다른 정상 항목 처리 | DB 오류는 실패 청크 롤백 후 작업 중단 |
| 이미 커밋한 항목 | 유지 | 유지 |

수동을 유지한 이유는 기존 건별 부분 성공 계약과 응답을 보존하기 위해서다. 50건이면 성능 문제가 없다고 입증한 것은 아니다. 자동은 여러 건의 쓰기와 커밋 비용을 줄이는 대신 청크 전체가 롤백될 수 있다. 업무 정책이 바뀌면 엔티티/수동 검증과 자동 후보 조회/UPDATE 조건을 함께 변경해야 한다. 자동의 변경 행 수 차이는 제외로 집계하며 상세 실패 사유를 반환하지 않는다.

| 대상 스냅샷 | 설계 검토 | 지연 삽입까지 실행 대상 명단을 고정해야 할 때 별도 구현 |
| 실행 이력/체크포인트 | 설계 검토 | 서버 중단 후 실행 상태 추적과 이어서 재개할 요구를 별도 구현. 현재 로그와 수동 재실행은 이를 대체하지 않음 |
| Partitioning | 적용 필요성 검토, 병렬 실측 없음 | 단일 작업자가 처리 기한을 못 지킨 근거 없음. 병렬 잠금/부하/분할 책임 증가 |
| Kafka/Outbox | 적용 필요성 검토, 발행 실험 없음 | 완료 후 외부 이벤트를 신뢰성 있게 발행해야 할 때 검토. 현재 완료 조회/쓰기 비용과 별도 문제 |

## 100건 설정 회귀 검증

일반/perf 100건, 완료 전용 Controller 분리 후 컴파일과 기존 정산 테스트 19개를 실행해 통과했다. 생성 perf Controller와 생성 요청 DTO를 제외한 임시 구성에서도 bootJar와 같은 19개 테스트를 통과했다.

완료 전용 구성의 임시 서버와 전용 PostgreSQL에서 110건을 실행해 2개 청크 커밋, 같은 cutoff 재실행 0건, 상태/금액/버전/감사 필드 불일치 0을 확인했다. 별도 100건 중 미래 대상 1건은 전체 행이 유지되고 나머지 99건이 완료됐다. 임시 데이터 제거 후 기존 38,591건의 전체 행 지문이 유지됐다. 이는 설정과 진입점의 소량 회귀 검증이며 성능 Before/After를 다시 측정한 결과가 아니다. 경합과 오류 주입 롤백은 위 과거 검증 기록을 사용하며 이 소량 검증에서 다시 실행하지 않았다.
